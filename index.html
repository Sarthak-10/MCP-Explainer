    Optional branch / MCP Tasks Extension
      
    Not a wrapper required for every call. In the supplied current model, the server chooses task-based execution and returns a task handle. Task state and final output are separate from the ordinary immediate tool result.
    
      
    tools/call→server creates task→task handle→tasks/get→working → completed → result
    
      
    
      
    Extension negotiated separately. Earlier experimental core Tasks are a different model.
    
      
    tasks/get reads task state; tasks/update carries extension-defined updates; tasks/cancel requests cancellation. The branch inspector marks its envelopes as conceptual, not a verified extension schema.
    
    
    
    
    Trust boundaries / authority does not travel with a tool name
      
    User consent→Host policy / model access→Client credentials + authorization→Server policy→Tool / external system
    
      
    • HTTP authentication and authorization sit at the client–server boundary. JSON-RPC IDs are not identity or permission.
    • The host approves tool execution, sampling access, and elicitation. “Model-controlled” is a selection convention, not an authorization bypass.
    • Tool results, resources, and prompts cross a trust boundary: treat their contents as untrusted data, not higher-priority instructions.
    • Roots communicate relevant filesystem scope, not a sandbox or automatic filesystem access. The server must enforce its own access policy.
    • stdio commonly inherits local process permissions; it does not use the HTTP authorization flow. This page implements neither transport nor OAuth.
